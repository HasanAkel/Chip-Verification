## A. What OpenTitan is

- Open-source root-of-trust silicon IP project, stewarded by lowRISC with
  Google, Western Digital and others; produces the "Earlgrey" SoC. [VS:
  opentitan.org, github.com/lowRISC/opentitan]
- Root of trust = the first chip to run at power-on; verifies boot firmware
  chain, holds keys in hardware, provides attestation. Beginner framing:
  immigration officer stamping each boot stage's passport. [VS: opentitan.org/book]
- Google Titan M2 (Pixel 6+) is built on OpenTitan; Earlgrey production
  tapeout announced Oct 2024 (TSMC 16nm per press coverage). [VS: Google
  security blog; lowRISC announcement. The *node* is press-reported, not in-repo.]
- Boot chain (simplified): ROM → ROM_EXT (in flash, verified) → owner
  firmware; life-cycle controller (lc_ctrl) gates debug/features across
  states (RAW→TEST→DEV/PROD→RMA); key manager (keymgr) derives ephemeral
  keys. [VP: block presence in hw/ip + doc/glossary.md; detailed semantics
  U-level here, documented in opentitan.org/book]

## D. Interconnect and AXI — definitive

- Internal protocol: **TL-UL (TileLink Uncached Lightweight)**. Bus agents:
  `tl_agent` only; DV lib list shows no AXI/VIP. [VP: hw/dv/sv listing]
- Crossbar: GENERATED. Sources `hw/top_earlgrey/ip/xbar_main/data/autogen/
  xbar_main.hjson` + `.gen.hjson`, generated by `tlgen` (util/tlgen.py).
  [VP: paths verified]
- AXI in `hw/`: file search found ZERO matches. [VP: dir /s /b *axi*]
- Contrast with Track 1: OpenCores AXI4 crossbar (handwritten muxes/demuxes)
  vs OpenTitan generated TL-UL fabric. Protocol concepts (handshakes,
  bursts, IDs) map; pin-level protocol does not.

## F. Running/testing on this laptop (Windows 11, 16 GB)

1. Official DV flow: UVM (SystemVerilog), simulators VCS/Xcelium/Questahome-
   class commercial; `dvsim` (Python) drives regressions; Bazel builds SW;
   Verilator supported for some flows. [VS: opentitan.org/book/doc/getting_started]
   Commercial sims: unavailable here → official per-block UVM regression
   impractical on this laptop.
2. Lightweight paths: Verilator is first-class for OpenTitan (chip-level
   Verilator sim exists) [VS]; Icarus is NOT officially supported for DV
   environments [U - to test]. WSL2 recommended path for Linux tools [VS:
   install docs]. cocotb: not part of OpenTitan flow [U].
3. Day-one environment: uart DV exists from 2019-08-31 with Makefile +
   FuseSoC cores (`.core` files) — rebuilding that tree needs: FuseSoC,
   older UVM (VCS-era), tlul agents from same commit, generated RAL model
   (uart_reg_block.sv handwritten at that time [VP: file list]). RISKS:
   tool drift, missing `dvsim` (didn't exist), vendored lowrisc_ip utils.
4. Pitfalls for replays: reggen/topgen outputs are committed at some epochs
   and generated at others; `.core` file format churn; submodule/vendor pins
   (ibex); path renames (hw/ip reorganizations); Python version drift.
   Mitigation: `git worktree` at tag/commit, never modify C:\cv\opentitan
   master checkout.
